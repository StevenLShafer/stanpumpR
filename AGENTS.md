# AGENTS.md — AI Agent Orientation

**stanpumpR** is an R package + Shiny app for PK/PD simulation. It calculates and plots predicted plasma ($C_p$) and effect-site ($C_e$) concentrations for IV and extravascular anesthetics using **analytical closed-form 3-compartment solutions** (no ODE solver). Stack/version details: `DESCRIPTION`. Entry point: `app.R` → `stanpumpR::run_app()`.

---

## Architecture: Reactive Request-to-Render Pipeline (`R/app_server.R`)

*Full details available in `docs/architecture.md`*

1. **Inputs**: Patient covariates, dose grid (`rhandsontable`), clinical events, plot settings.
2. **Validate**: `doseTableClean()`, `eventTableClean()`, `testCovariates()`.
3. **Resolve PK**: `recalculatePK()` calls `getDrugPK()`, which converts covariates → micro rate constants → eigenvalues (`cube()`) → $k_{e0}$ (solved from `tPeak` by `ke0FromTPeakBolus()`, or `ke0FromTPeak()` for an oral `tPeak`) → exponential coefficients.
4. **Simulate**: `processdoseTable()` calls `simCpCe()`, which first expands any `qd`/`bid`/`tid`/`qid` dose into its repeats to the end of the plot (`scheduled.R`; returned as `$scheduled` for export) and any `Plasma target` / `Effect site target` rows into a TCI infusion schedule (`tci.R`, Shafer & Gregg 1992; returned as `$tci` for the rate panel and export), then dispatches to:
   - `advanceClosedForm0.R` (IV, standard PK)
   - `advanceClosedForm1.R` (time-varying PK with events)
   - `advanceClosedFormPO_IM_IN.R` (extravascular 1st-order absorption: PO, SL (sublingual), IM, IN, SC (subcutaneous: the incretins, insulins, enoxaparin and fondaparinux, carried on the RA tissue depot; `R/subcutaneous.R`) and RA, regional anesthesia, a local anesthetic injected into tissue — `ka_RA`/`bioavailability_RA`/`tlag_RA`, units `raUnits`; tests `test-route-ra.R`)
   - `advanceMichaelisMenten.R` (numerical, with saturable, Michaelis-Menten elimination — the one non-superposable engine, for phenytoin, GHB, exenatide and cetagliptin; a drug declares it with a `michaelisMenten` block (`vmax`, `km`, per-product `saltFactor`, optional `kConversion`/`ka_IM` for a prodrug route like fosphenytoin's `mg PE`; optional `clLinear` for a parallel linear clearance (with `vmax` 0 when there is no saturable elimination), `saturableSC` for exenatide's zero-order-then-saturable SC input, `rapidBinding` or `targetBinding` for target-mediated disposition (linagliptin, vildagliptin), and `kaTransit` for a transit compartment before the oral depot; a PK set with `cl2 > 0`, or `k23`/`k32` in the block (GHB; both or neither, mapped to the same state as Q = k23 V, Vp = V k23/k32), adds a peripheral compartment, and elimination and distribution act on the unbound concentrations). Integrates the whole dose table at once, so `simCpCe()` dispatches here before it splits oral formulations; tests `test-michaelis-menten.R`)
   - `advanceTransitChain.R` (**exact**, by matrix exponential — for a transit-chain absorption whose repeated eigenvalue no closed-form coefficient can carry: enalapril, whose eight identical Erlang transit compartments share one eigenvalue eight times over, so `separateEigenvalues()`'s 1e-8 nudge would make the partial-fraction coefficients scale as 1/nudge⁷. The system is linear, so this is not a numerical solver: it is exact to rounding, like the closed forms, and unlike `advanceMichaelisMenten()` it approximates nothing. A drug declares a `transitChain` block (`n` chain compartments, the first n−1 emptying at `ktr` and the LAST at the PK set's `ka_PO`; `kMetabolic`, the share of the PK set's `k10` that forms the metabolite rather than leaving the body; and an optional `metabolite` giving the receiving drug's `name`, its own chain `n`/`ktr` — every compartment of which empties at `ktr`, the asymmetry being the source's — plus `v`, `kel` and optional `k12`/`k21`). The engine advances both moieties together and returns the metabolite's columns itself, because the closed-form metabolite route convolves exponential amplitudes a defective system does not have, so `simCpCe()` dispatches here before `runEngines()`; `getDrugPK()` refuses the block alongside an `X$metabolite`, several oral formulations, saturable absorption, parallel systems, Michaelis-Menten elimination, an osmotic/molar basis, pulsed or zero-order oral release, a dose-phase split, dose-dependent parameters or an INR. One matrix exponential per distinct step length, memoised on it and augmented with a unit-rate state so the same one serves the homogeneous propagator and the rate response; the non-uniform time line repeats a few dozen step lengths across thousands of points, so a drug costs a few dozen exponentials. No effect site and no time until threshold, structurally: a defective system leaves no exponential amplitudes for `recoveryStates()`. Tests `test-transit-chain.R` (the Erlang density, the analytical bolus and constant-rate solutions, the closed-form oral engine where the chain degenerates, and an independent RK4 of all 13 states), `test-drugs-enalapril.R`)
5. **Plot & Render**: `simulationPlot.R` generates `ggplot2` output.

**% MEAC overlay** (`R/meacOverlay.R`): Graph Options **% MEAC on opioid panels** (`input$showMEAC`, scenario option `showMEAC`) draws each opioid's effect-site % MEAC as a thin black line on its own panel, labelled at the right-hand edge, on ONE scale shared by every opioid panel (its top is the highest % MEAC any opioid reaches, `meacOverlayBreaks()`, mapped onto each panel's data range), so a parent and a metabolite of very different potency can be compared at a glance. It shares the right-hand edge with *Time until threshold*: ticking either unticks the other, and `simulationPlot()` drops the overlay when `plotRecovery` is on or under normalization. Scenario `hydrocodone-hydromorphone-meac`; tests `test-meac-overlay.R`.

**Peripheral compartments** (`R/compartments.R`): Graph Options **Peripheral compartments** (`input$showCompartments`, scenario option `showCompartments`) adds, directly under each drug's panel (V1) and before its TCI panel, one panel per further compartment: `V2`, `V3` (drug's concentration units), an inhaled agent's `MRG`/`FG` (gas states 4 and 5, from `gasDrugEntries()`), and `Depot`, the bioavailable amount still to be absorbed (all depots summed; enters after the lag; unit from `depotUnits()`). Every engine returns columns `C2`, `C3`, `Depot` (zero where absent); the peripheral concentrations are exact, read off the plasma states as `k21 * sum(s / (k21 - mu))` by `peripheralConcentration()` (the same mode relation `convertState()` uses), so they are always computed and never enter `simulationKey()`. `simCpCe()` lifts them into `$compartments` with `liftCompartments()` (only the compartments the drug has; none for osmotic or INR drugs); a metabolite parent also returns `$metaboliteCompartments`, which `foldMetabolites()` adds to the metabolite drug's (`compartmentsOwn` → `compartments`, as `wideOwn` → `wide`). The panel's facet value is `"<drug> <compartment>\n(<unit>)"` (unique, read by the hover and the click through `compartmentSeries()`); its strip shows only the compartment (`compartmentPanelLabel()`). Off under normalization. Help page `inst/help/models/compartments.md`; scenarios `propofol-peripheral-compartments`, `oral-morphine-depot`; tests `test-compartments.R` (matrix-exponential reference for every engine).

`processdoseTable()` re-simulates only the drugs whose inputs changed: `drugs()` passes it the previous result as `cache`, and a drug whose `simulationKey()` (PK, dose rows, PK events, plot length, recovery switch) is unchanged reuses its own stored simulation. `foldMetabolites()` always re-runs on top.

**Antiseizure drug interactions** (`R/antiseizureInteractions.R`): Graph Options **Include antiseizure drug interactions** (`input$antiseizureInteractions`, scenario option `antiseizureInteractions`, enabled while the dose table holds an interacting pair or carbamazepine) applies the pharmacokinetic interactions among the epilepsy drugs — enzyme induction (carbamazepine, phenytoin, phenobarbital) of lamotrigine, valproate, topiramate, tiagabine, lacosamide, eslicarbazepine, cenobamate, zonisamide (Silva 2025 `1.63^INDDL`) and ethosuximide (Giaccone 1996, pooled `CL x1.66`), ethosuximide's own induction of lamotrigine (Hagemann 2024, adult `CL x1.16`; larger in children), inhibition and albumin displacement (valproate, including a variable `CL x0.85` on ethosuximide from Pisani 1984), zonisamide on phenytoin's Km, and carbamazepine's autoinduction. The interactions and their verified PMIDs are `inst/extdata/antiseizureInteractions.csv` (built by `data-raw/antiseizureInteractions.R`, checked by `test-antiseizure-interactions.R`); 35 applied rows, the four required victims (phenytoin, valproate, lamotrigine, carbamazepine) among them, plus zonisamide and ethosuximide as victims and ethosuximide as a perpetrator (lacosamide is induced by all three of carbamazepine, phenobarbital and phenytoin — the phenytoin row from Contin 2013, `CL x1.44`); 14 cross-check rows (the consensus reviews Patsalos & Perucca 2003, Riva 1996, Spina 1996, Tanaka 1999 and the secondary lamotrigine/zonisamide/valproate-binding/ethosuximide studies) and 10 recorded (not applied). Several inducer factors (topiramate, tiagabine, lacosamide, ethosuximide) are *pooled* any-inducer covariates applied per inducer row, which over-predicts a multi-inducer regimen under additive-excess — a structural limitation flagged in `docs/antiseizure-interactions-review.md` for the engine-level review. Each interaction is a saturable function of the perpetrator's own plotted concentration, `fold(C) = 1 + (Fmax-1) C/(EC50+C)`, calibrated so `fold(Cref)` is the published categorical factor at the perpetrator's typical band value `Cref` (EC50 defaults to the band's lower edge; `ec50_basis` records it); inductions run through an enzyme-turnover model `dE/dt = kdeg(fold-E)` with a de-induction half-life of 86.1 h (Punyawudho 2009), inhibition and displacement are immediate. Several inducers of one victim add in their excess, `1 + sum(Ei-1)`; inhibitions multiply. `processdoseTable(..., antiseizureInteractions = TRUE)` calls `applyAntiseizureInteractions()` after every drug is simulated alone: it computes each victim's multipliers from the perpetrators' concentrations, cuts them into near-constant segments (`asmSegments()`, `ASM_INTERACTION_TOLERANCE`), rebuilds the victim's PK with one set per clearance segment (`asmSegmentPK()`, which needs the covariates `getDrugPK()` now keeps for every `asmInteractionVictims()` drug) and re-simulates through the event engine, or for phenytoin feeds Vmax/Km multipliers to `advanceMichaelisMenten()` via `PK$interactionMM`; victims are also perpetrators, so it iterates to a fixed point (`ASM_INTERACTION_CONVERGENCE`, `ASM_INTERACTION_MAX_ITERATIONS`). `simCpCe()` reads a victim's segment events from `PK$interactionEvents`. Each changed drug is drawn beside its own uninteracted curve through the companion mechanism (`addAntiseizureReferenceEntries()` builds a `companionOf` entry `"<drug> (no interactions)"`; `alternativeModelParent()` maps it back). Help page `inst/help/models/antiseizure-interactions.md` (generated blocks `antiseizure-interaction-table`, `antiseizure-interaction-sources`); scenarios `valproate-lamotrigine-inhibition`, `carbamazepine-lamotrigine-deinduction`, `carbamazepine-autoinduction`, `phenytoin-valproate-displacement`, `carbamazepine-phenytoin-induction`. Not modelled: unbound phenytoin (totals are plotted), metabolites (the epoxide), drugs outside the group, and any interaction only a product label quantifies (rows with `status` `recorded`).

**Dose table lifecycle**: edits land in a draft held by an `{undomanager}` (`doseTableHistory()`, with `doseTableDraft()` a thin reactive over its `$value`) that owns the undo/redo history; `Apply` commits it to the canonical `doseTable()`; `doseTableClean()` (cleaned via `cleanDoseTable()` in `input-tables.R`) is what the rest of the pipeline actually reads. Clicking the plot to add/edit a dose bypasses the draft and applies immediately, and any direct write to `doseTable()` resets the draft and clears the history.

**Startup** (`R/startup-drugs.R`): a session starts with an empty dose table (`doseTableBlank`) and, unless the URL restores a bookmark with drugs in its dose table, `app_server()` shows a modal of checkboxes grouped by the CSV's `Category` column (`DRUG_CATEGORIES` order), each category a collapsed `<details>` section whose summary gives its drug count (and, through `app.js`, how many are ticked), with nothing ticked. **Start** writes `startupDoseTable()` to `doseTable()` through `setDoseTable()`, in the table's current time format (its times are all `"0"`); with the four drugs of `STARTUP_DRUGS_DEFAULT` ticked that is exactly `doseTableInit`, the table the app opened with before the menu and the one the tests start from. Shiny "restores" from any query string, so `?debug=1` alone is not a bookmark: `isBookmarkRestore()` requires a `DT` value, and `onRestored()` returns early without one. The weekly welcome text (`show_intro_modal` from `app.js`) is rendered into the open menu rather than replacing it. Tests: `test-startup-drugs.R`.

**Deep links** (`R/deep-links.R`): `?scenario=<id>` opens a fresh session with that teaching scenario loaded (through `helpServer()`'s `loadScenario()`, after the dose-table history exists, since `setDoseTable()` writes it) and `?help=<page-id>` opens the Help tab on that page with an empty simulator behind it (the session's `doseTableBlank`); either skips the startup menu and the welcome. `deepLinkFromQuery()` validates both against the scenario list and the page registry; a bookmark's dose table wins over `?scenario=`. The first change rewrites the address bar into an ordinary bookmark. Every scenario page prints its own link. Help page `inst/help/sharing.md`. Tests: `test-deep-links.R`.

**Illicit drugs** (`R/illicit-drugs.R`): drugs in the `Illicit drugs` category (`ILLICIT_DRUG_CATEGORY`) are opt-in, evidence-labelled research models of drugs of abuse (diamorphine, cocaine, methamphetamine, LSD, psilocybin, MDMA and GHB; `R/drugs_diamorphine.R` and the files beside it). Every one is **plasma only** (`tPeak` 0, `MEAC` 0, no band), and each offers dose units **only** for a route whose input model the human evidence identifies: `inst/extdata/illicitRouteRegistry.csv` carries one row per drug and route with its `route_status` (calibrated / anchored / observed / unsupported), `parameter_status`, analyte, matrix, dose basis and source, and `test-illicit-registry.R` refuses a route that has units without an `offered` row, or an offered route whose input model is not identified. There is no pulmonary route, so a smoked route is recorded and not offered; it must never be aliased to `IN`. An input SHAPE the engine lacks is a different case from a missing parameter: MDMA's published zero-order depot filling is DISCRETISED as two lagged half doses at the quarter points of its window, measured against a numerical evaluation of the exact solution in `test-drugs-MDMA.R` (0.01% at the peak, 0.53% over the curve), so it stays a `published_fit`. An engine the library lacked is a third case, and the answer is to build it, not to approximate: GHB (Chen 2020) is two compartments with saturable elimination, so `advanceMichaelisMenten.R` gained its optional peripheral compartment for it. Where a source's dose basis differs from the plotted analyte, the **unit names the basis** (`g PO oxybate`): GHB's dose is the salt and its curve the acid, 21% apart, carried by a `saltFactor` and an exact rescaling of `vmax` and `km`. A new illicit model is validated against sources it was *not* fitted to where any exist — GHB against Liechti 2016 (+6%, −1%) and Palatini 1993 — because that is what catches a basis error. Help page `inst/help/models/illicit-drugs.md`, which carries the generated block `illicit-pk-table` (`helpIllicitPKTableMarkdown()`): one row per illicit drug at the reference adult giving the analyte plotted, the structure, V1, the elimination (a clearance, or Vmax and Km where it saturates), the absorption and the half-life, built from the models so it cannot drift. A persistent checkbox, **Show illicit drugs** (`input$showIllicitDrugs`), off by default, gates them: when off they are not offered in the dose-table autocomplete or the Add a dose dialog (`drugChoices()` → `visibleDrugNames()`), and the startup menu never lists them (`startupDrugChoices()`); when on they appear, with their names drawn in red in the dose table (`createHOT()` renderer, reading the `drug_defaults` global by `Category`). Restoring a bookmark whose dose table holds an illicit drug turns the opt-in on so the drug is not hidden from its own table. Tests: `test-illicit-drugs.R`.

**Scheduled doses** (`R/scheduled.R`): a bolus, PO, SL, IM, IN or SC unit followed by `qd`, `bid`, `tid` or `qid`, or an SC unit followed by `qwk` (once weekly) (`"mg PO bid"`, `"mg SC qwk"`; the full list is `scheduledUnits`, intervals in minutes are `ALL_SCHEDULE_INTERVALS` in `R/constants.R`: the daily `SCHEDULE_INTERVALS` plus `WEEKLY_SCHEDULE_INTERVAL`) gives the dose at the time entered and repeats it every interval until the end of the plot. Rules, per route (IV, PO, SL, IM, IN, SC) within a drug: a scheduled dose of 0 at any frequency stops the sequence (an ordinary dose of 0 does not, except on the oral and sublingual routes, below); a later non-zero scheduled row replaces the running sequence from its own time; two scheduled rows at the same time keep the last one entered. On the oral and sublingual routes, taken as one, ANY later oral or sublingual dose (scheduled or not, any oral form, 0 included; not an oral rate unit or a row with no readable time) ends the running oral or sublingual schedule (`scheduledSequences()`). **Skip next dose**, a button in both plot dose dialogs while the clicked drug has a scheduled dose on any route at or after the time clicked (never an infusion or a TCI target, which are delivered continuously and have no next dose), writes the skip into the dose table by those rules — a 0 dose of the schedule's route at the skipped time (an ordinary 0 on PO and SL; a scheduled 0 in the schedule's own unit on every other route, where an ordinary 0 does not stop a schedule) and the scheduled row again one interval later, unless the schedule ends first (`skipNextScheduledDose()`). As with TCI, the repeats never enter the editable dose table: `expandScheduledDoses()` runs first in `simCpCe()`, turning each scheduled row into its base unit plus the repeats, so the engines and `doseRoute()` only ever see ordinary units; the repeats are returned as `$scheduled` (Drug, Time, Dose, Units), carried through the simulation cache, and merged with the TCI rows into the exported dose table by `exportDoseTable()`. Which drugs offer the frequencies is set by their `Units` in `drugDefaults_global.csv` (opioid analgesics, antibiotics, steroids; not the anaesthetics, TCI-only drugs, or mannitol, which is infusion-only). Tests: `test-scheduled.R`.

**Stop** (`R/stop-administration.R`): both plot dose dialogs offer **Stop <drug> at <time>** while the clicked drug has something running at the time clicked — an infusion (any rate unit, any route), a TCI target (the latest of target and manual rate on the intravenous route; at one time the target wins), a schedule with a repeat still to come, or an inhaled agent's setting (`ongoingAdministration()`). It writes only the 0 rows the existing rules read as a stop, at that time (`stopAdministration()`): a 0 rate, a 0 target, a scheduled 0 in the schedule's own unit (which stops every route), a 0 setting. Tests: `test-stop-administration.R`, `test-stop-administration-server.R`.

**The TCI API** (`R/tci-api.R`, `R/tci-api-server.R`; normative reference `docs/tci-api.md`, help page `inst/help/tci-api.md`): a stateless HTTP API under `/tci/v1` that hands a TCI pump controller its next rate for one drug in one patient, re-deriving the model state from the controller's delivery history on every request (the STANPUMP principle). `tciNextRate(request)` (exported, pure R, no Shiny, no plumber) takes the body as `jsonlite::fromJSON(txt, simplifyVector = FALSE)` gives it, rebuilds the seven-amplitude state from the history (rate changes, delivered segments, hand boluses, infusate changes), projects it through the declared `timing.latency`, calls the app's `tciRate()`, applies `pump.maxRate` / `minRate` / `rateResolution` (always rounding down) and returns the response list (`rate`, `segment`, `fallback`, `timing`, `state`, `prediction`, `model`, `warnings`); validation raises the classed condition `tci_api_error` (`status`, `code`, `message`, `pointer`). Field names, unit tokens (the library's spellings: `mL/hr`, `mcg`; one closed list, no aliases), error codes, HTTP statuses and the `TCI_API_*` bounds in `R/constants.R` are fixed by `docs/tci-api.md`: within `/tci/v1` only add, never change a meaning. `tciApiRouter()` / `run_tci_api()` wrap it in plumber (`inst/api/entrypoint.R` for `rsconnect::deployAPI()`, `inst/api/openapi.json` hand-written); shinyapps.io does not host it. Tests: `test-tci-api.R` (the closed loop reproduces `tciSchedule()` rate for rate at zero latency; every error and warning code) and `test-tci-api-http.R` (in-process `pr$call()` on `rookRequest()` from `helpers.R`; skipped without plumber). [FauxTCI](https://github.com/StevenLShafer/FauxTCI) (served at https://stevenlshafer.github.io/FauxTCI/) is a browser pump built to this contract: a JavaScript port of the controller validated against fixtures that its `test/fixtures/generate.R` produces from this package, so a change to `tciNextRate()`'s numbers or to `docs/tci-api.md` is a change FauxTCI must follow.

**Time units** (`R/utils-time.R`; `docs/architecture.md#time-units`): minutes / hours / days / weeks are entry and display only — the engine, events, scenarios, `input$maximum` values, `simulationKey()` and exported Time columns stay in minutes. The app opens in elapsed time (`TIME_MODE_DEFAULT`, `"relative"`, which `timeFormat()` also takes for an unknown mode; actual/clock time is a choice for minutes and hours, and a bookmark that saved neither a format nor a Time Display is still read as clock, which it was made in). The dose table holds its Time strings as typed, in the format (`c(unit, mode)`) recorded by `doseTableFormat()`; `doseTableClean()` reads them with that record, never the selectors. Write a new table with its format through `setDoseTable()` (or `timeApi` from outside `app_server()`); a selector change is converted by one observer (`rebaseDoseTimes()`), and `plotInfo()` waits while record and selectors disagree. **Max time** and **Min time** are sliders whose values stay in minutes in every unit (`input$maximum`, `input$minimum`), shown in the unit by `formatSliderMinutes()` in `app.js`, which Shiny's own slider updates would replace, so the slider's `onUpdate` puts it back; their range and step are per unit (`timeSliderRange()`: 0 to the unit's longest `MAX_TIMES` length, in `TIME_SLIDER_STEPS`), reset on a change of unit by `syncTimeSliders()`, and `plotInfo()` waits (`sliderPending()`) until the browser reports the snapped values. Min time moves only the window drawn: everything is simulated from 0, `processdoseTable(plotMinimum =)` refines every time line inside the window (`withGridWindow()`, `equispaceTimes()` in `R/simulationTimeGrid.R`; part of `simulationKey()`), `simulationPlot(xMinimum =)` draws each series from the window's start (`seriesFromMinimum()`) so each panel scales to it, and the ticks come from `axisTimeStep()` / `axisTimeBreaks()` (a `MAX_TIMES` length from 0 keeps its own ticks). TCI rows and inhaled agents only on plots of a week or less. Tests: `test-utils-time.R`, `test-time-units-server.R`, `test-simulationTimeGrid.R`, `test-stop-administration-server.R`.

**Testing/scripting entry point**: `simulateDrugsWithCovariates()` is the exported, Shiny-free API (loops `getDrugPK()` → `simCpCe()` per drug) — used by tests and vignettes to drive the PK/PD core without the app.

**Minto / Schnider** (`R/alternativeModels.R`): a Graph Options checkbox (`input$mintoSchnider`, enabled while propofol or remifentanil is dosed) runs Schnider's 1998 propofol and Minto's 1997 remifentanil models, the models in most TCI pumps, beside the library's Eleveld models. Each is a *companion entry* of the drug list, named `propofol (Schnider)` / `remifentanil (Minto)` with `$companionOf` and `$modelLabel`: `recalculatePK(alternativeModels = TRUE)` builds it through `getDrugPK(model = ...)`, `processdoseTable()` simulates it on the parent's doses with recovery off (the time until threshold stays on Eleveld), and `simulationPlot()` draws it as a second line in the parent's panel (colour from `alternativeModelColor()`, own legend entry) and its TCI pump as a second line on the parent's rate panel. Companions are excluded from the MEAC sum, the interaction panel and the opioid-MAC interaction; `alternativeModelParent()` maps a companion's series name back to the parent for the hover and the click. Minto supplies `ke0` as a function of age with no `tPeak`, which `getDrugPK()` now accepts, solving the time to peak effect from `ke0`. A model whose covariate terms give a non-positive parameter for the patient is skipped and `alternativeModelProblems()` says why (shown as a notification). Help page `inst/help/models/minto-schnider.md` (generated block `minto-schnider-table`); Both keep the James lean body mass (`lbmJames()`), deliberately, so they behave as the pumps do: it is a parabola in weight that falls past a BMI of 43 (men) or 36 (women), which is part of what the companions teach; the library's own models use Al-Sallami. Scenarios `eleveld-vs-minto-schnider`, `tci-eleveld-vs-minto-schnider`, `james-lean-body-mass` (scenario option `mintoSchnider`). The Open TCI commentary, `inst/help/opentci.md` (linked from the History page), carries the generated block `james-lbm-figure` (`helpJamesLBMFigure()`), an inline SVG of the James parabola drawn from `lbmJames()` and `ffmAlSallami()`. Tests: `test-minto-schnider.R`.

**Simulation API** (`R/api.R`, `inst/plumber/plumber.R`; spec `inst/apidocs/api.md`, published at https://stanpumpr.io/api; help page `inst/help/simulation-api.md`): `apiSimulate(request)` validates a request (patient, dose table, duration, `timeUnit`, events, output grid), runs `simulateDrugsWithCovariates()`, and returns `meta`/`patient`/`drugs`/`doses`/`timeseries`/`warnings`, always in minutes, kg, cm and years; `apiFormatResult()` serialises it as JSON, CSV, xlsx or XML; `run_api()` serves `POST /simulate`, `GET /drugs`, `GET /health` with plumber (a Suggests). The requested output times are simulated exactly, not interpolated: `withOutputTimes()` adds them as extra points to every `simulationTimeGrid()` line, and nothing is added outside it. Request errors are `stanpumpr_api_error` conditions (HTTP 400). Inhaled agents are refused. Illicit drugs need `options.allowIllicitDrugs`. The spec is the integrator-facing documentation: `apiDocsHtml()` (`R/api-docs.R`) renders it into a self-contained page that `run_app()` serves as the resource path `api` (so `<app>/api`) and `run_api()` serves at `/`; keep it in step with the code. Tests: `test-api.R`, `test-api-docs.R`.

## Key Rules

- **Adding a drug** requires all four (full procedure: `docs/adding-a-drug.md`):
  1. `R/drugs_<name>.R` (covariate model function)
  2. `inst/extdata/drugDefaults_global.csv` (row with colors, units, MEAC, and the `Category` that lists it in the startup menu)
  3. `tests/testthat/test-drugs-<name>.R` (unit test — pin values with `expect_equal_rounded()` from `tests/testthat/helpers.R`)
  4. `inst/help/drugs/<name>.md` (the narrative for the drug's generated help page; `test-help-drugs.R` fails without it)

- **Antihypertensives** (`R/antihypertensives.R`, `docs/antihypertensives.md`, help page `inst/help/models/antihypertensives.md`): evidence-gated, and **no drug in the library plots a blood pressure**. The commonly used antihypertensives share no defensible concentration-to-BP model, most have no complete published PK either, and where a response was fitted the endpoint is usually not a resting pressure (exercise SBP, exercise HR, isoproterenol-induced tachycardia, urinary sodium, ACE inhibition, renin activity, a MAP/HR resistance proxy, or the *probability* of crossing a MAP threshold). So the deliverable is a registry, not a curve per drug: `inst/extdata/antihypertensiveRegistry.csv` holds one row per **model record** (complete at the ingredient level in the five classes it enumerates — ARBs, ACE inhibitors, CCBs, beta blockers, diuretics — against an approved-ingredient list no FDA register was reachable to confirm, so `test-antihypertensive-registry.R` holds the five class lists where they can be corrected and re-checked; a row whose label could not be retrieved carries `source_type` `ingredient_catalog`, asserts ingredient, class, route and formulation only, and leaves `matrix` NA; `docs/antihypertensives.md` section 13) (molecule x formulation x route, and for a fitted source also population x endpoint x publication, keyed by `model_id`), with independent `pk_evidence` / `pd_evidence` / `execution_status` / `bp_simulation_enabled` / `external_validation_status` fields; `inst/extdata/antihypertensiveParameters.csv` holds every transcribed number with its unit, matrix, population, endpoint, fitted/fixed/derived status, the uncertainty *type the source itself names* (`not_reported` where the source prints a +/- and never says what it is) and whether it was verified against the primary source. Both are rebuilt by `data-raw/antihypertensiveRegistry.R` and checked by `test-antihypertensive-registry.R`, which asserts that `bp_simulation_enabled` is FALSE everywhere, that no catalog row carries a parameter, and that **no executable record depends on an unverified number**. Six records are implemented as drugs, all concentration only: `clevidipine` (whole blood; V1, V2 and Q *derived* uniquely from the reported CL, Vss and both half-lives, corroborated by the paper's own ">80% of AUC in the initial phase") `fenoldopamPediatric` (named for its population, as `methylphenidatePediatric` is, so it cannot become an adult default; there is deliberately no adult `fenoldopam`) and `carvedilol` (apparent oral, **zero-order release**: `R/oral-zero-order.R` is the engine mode it needed, since Hwang 2023 reports first-order and dual absorption both failed to describe its densely sampled absorption). A drug declares `oralZeroOrder = list(duration = <min>, lag = <min>)` and `simCpCe()` rewrites each `mg PO` dose into the constant-rate rows that deliver it, which the classification then treats as an infusion on the apparent oral parameters -- no ka, no bioavailability, both being inside the apparent scale. Overlapping releases are **summed**, because the infusion rate on the time line is a step function and independent row pairs would replace rather than add. `getDrugPK()` refuses the mode alongside an active metabolite, several oral formulations, saturable absorption, parallel systems, Michaelis-Menten elimination, an osmotic/molar basis, pulsed oral release or an active first-order oral depot (a positive `ka_PO`/`ka_PO2`, which the expansion would leave unused), and `expandOralZeroOrder()` itself refuses a standing oral rate row beside a release, which would be replaced rather than added to. Tests: `test-oral-zero-order.R` (the curve is checked against an independent closed-form constant-rate solution), `test-drugs-carvedilol.R`. `azilsartan` and `chlorthalidone` (Tsai 2016, one phase-3 population fit; added 2026-10-17 from the full text, `docs/antihypertensives.md` section 10). Azilsartan's **dose basis is derived, not read**: the paper never says whether its doses are azilsartan or the medoxomil prodrug, a 20% difference, and its own simulated AUC values show the model received azilsartan, so `R/drugs_azilsartan.R` divides every apparent volume and clearance by 456.45/568.52 and a dose is entered as prescribed. Chlorthalidone applies the source's age and sex terms and deliberately applies **neither** of the other two: the cystatin C term because the Patient Profile has no cystatin C and serum creatinine is not a substitute for a filtration-only marker, and the BMI term because the printed equation is a product giving a zero volume at the reference BMI. Both reproduce all ten exposures the paper simulated, which the tests pin. `hydrochlorothiazide` (Van Wart 2013; apparent oral, plasma, renal covariate only, `R/drugs_hydrochlorothiazide.R`), whose published absorption is a **Weibull** (shape 2.84) and therefore an input shape with no constant `ka` at all: it is DISCRETISED into eight pulses of the default oral form (the `ORAL_PULSE_DEFAULT_FORM` key described above, which this drug is the first to need), absorbed at exactly 1.0 /h because that is the Weibull's own asymptotic rate constant rather than a fitted number, with the fractions and delays fitted MINIMAX -- the objective is the worst point, which is what the standard limits -- over the paper's four renal functions so that one pulse set serves every patient; `test-drugs-hydrochlorothiazide.R` checks the result against an independent numerical integration of the exact Weibull system at each of those four, not against the fractions, and its bounds ARE the documented standard (0.53% over the curve, 0.01% at the peak) rather than a loose fence. **Measure such an error at the pulse times**: it peaks exactly where a lagged depot starts and the approximation kinks, and `simulationTimeGrid()` puts a point at every dose time, so a uniform grid that steps over the kinks flatters the approximation -- on this drug a 0.02 h grid said 0.45% where the truth was 0.64%, and the six-pulse set it validated was outside the standard. Clevidipine was the registry's first `external_validation_status` other than `none` (enalapril is the second; see below): Ericsson's second 1999 paper (Eur J Clin Pharmacol, read in full) reports as measurements the V1, k10, bolus intercepts and fast-phase AUC share that the implemented record must derive, and the derivation applied to that study's own four numbers returns its measured V1 to 1.1% (0.09 of its standard error); because that paper is a complete fitted model the library deliberately does not plot, `execution_status` gained `complete_not_implemented` for records read and verified but used only to check an implemented one (`docs/antihypertensives.md` section 11). Four published endpoint relations are evaluable through `antihypertensiveEndpoint()` against a concentration the caller supplies; it returns the *change* the drug term predicts, never an absolute pressure, and every Emax is stored as a positive magnitude with an explicit direction so `C = EC50` gives half the **fall**. `enalapril` and its active metabolite `enalaprilat` (Faisal 2019, *Front Pediatr* 7:281; `docs/antihypertensives.md` section 16) are the registry's only ORAL record with **absolute** rather than apparent disposition: both moieties are cleared renally with no further metabolism, so fitting urine with serum closes the mass balance and bioavailability became a parameter of its own (0.606, against the literature's 60%). The parent is one compartment behind eight Erlang transit compartments, eliminating renally (`KREN`) and by conversion (`KM`); the metabolite is two compartments behind two more transits — which is why the library has `advanceTransitChain.R`. `enalaprilat` is metabolite-only (no `Units`, no `Category`, as `salicylate` is) and reads its parameters from the one place that defines them, `enalaprilatSet()`, so its help page and the plotted curve cannot drift; intravenous enalaprilat is deliberately NOT offered although the product exists and these parameters are absolute, because they were fitted to metabolite formed from an oral dose. The only covariate is weight¹ on the parent's central volume, normalised to the study mean 69.76 kg, so **there is no renal term although both moieties are cleared renally and by nothing else** — the sharpest form of that gap in the group. It is also the registry's second `external_validation_status` other than `none`, and the first validated against MEASUREMENTS rather than a second derivation: Arafat 2005 (*J Clin Pharm Ther* 30:319-28), two brands of 10 mg enalapril maleate measured with specific immunoassays, reports metabolite peaks of 54.8 and 57.2 ng/mL where this model gives 55.9 — and **that is what settles the dose basis**, which Faisal's text leaves open (whether F1 = 0.606 absorbs the maleate-to-base fraction 0.764), because a factor of 1.308 either way falls outside the measured range. **A basis ambiguity a source leaves open is often decidable from a study that never entered the fit**, which is the same reason the illicit-drug rule above demands an unfitted check. The same study disagrees by 1.9x on the metabolite AREA and its authors report their own 12-24 h concentrations as lower than the literature's, so that is recorded not reconciled (the Sun-1994-against-benazepril rule); and its PARENT is no check at all, the authors saying their enalapril peaks are "about 10 times those published in the literature" — **a validation source's own caveats about its assay are part of the comparison, and a study can check one analyte and not another**. Section 16 also records three corrections the full text forced on section 14.3, two of which are one mistake: **a quantity is not "ambiguous" because the parameter table alone does not settle it** — read the prose that defines the parameters before reaching for section 14.2's rule, and resolve a source's identifier against the index rather than transcribing it (section 14.3 cited a journal and DOI that do not exist, while every number it recorded was right). Before adding a record, check identifiability the way `docs/antihypertensives.md` section 4 does: for two compartments, CL + Vss + *both* half-lives closes the system, CL + Vss + the terminal half-life alone does not, and a formally closed system can still be too ill-conditioned to use (esmolol).

- **Rate constants must never tie**: every closed-form coefficient divides by a difference of two rate constants (`ke0 - lambda_i`, `ka - lambda_i`, `ka - ke0`, a metabolite's `mu - lambda`), so an exact tie is a division by zero. `getDrugPK()` runs ke0 and every `ka_*` through `separateEigenvalues()` (`R/metaboliteCoefficients.R`, a relative nudge of 1e-8) once, and returns the nudged values, so every engine sees rates that are already separate; the helpers that take a rate from elsewhere (`oralCoefficients()`, `effectSitePeakTime()`, `effectSiteCoefficients()`, the depot and ke0 guards in `advanceClosedForm1()`) apply it again. `calculateCe()` instead evaluates the limiting form when a step's log plasma slope equals `-ke0`. A new division by a rate difference goes through the same helper. Tests: `test-separated-rates.R`, `test-calculateCe.R`.
- **Debug logging**: `outputComments()`, active when `?debug=1` is in the URL.
- **Before starting a session on a bug**, take a quick look at master's recent commits and the open PRs: another session may already have fixed it. On 2026-10-14 two sessions fixed the References-panel citation links within an hour of each other, and the second PR had to be closed as superseded.
- **Adversarial review by another LLM** (the user runs ChatGPT and Gemini/"Argon" passes over this code, and considers them essential to the PK work): Claude has written nearly all of stanpumpR and **no other LLM writes its code** — an external review produces *leads, not findings*. Every specific claim it makes — a PMID, an applied factor, a statement of what the code does, a line of math — is an unverified lead, re-checked against the code and the primary source before anything reaches the repository. A meaningful fraction have been wrong: Gemini once fabricated an entire "13 hallucinated PMIDs" table (every PMID was in fact correct), and in a self-audit it stamped applied factors "exact match" that did not match the code (tiagabine ×2.665 for the real ×1.67, ethosuximide ×1.37 for ×1.66, two phantom "applied" cenobamate rows; 2026-10-24). A confident claim that announces itself as verified is the dangerous kind. So **when the user says Gemini/Argon (or any external LLM) will audit the code, the prompt Claude prepares for it MUST require a specific file path and line number for every finding and ask it to quote the exact line it is critiquing** — a line-anchored finding is one Claude can confirm in seconds, and its worst errors came from reconstructing files it had dropped from context (so give it the actual files, not a description). Gemini is a sharp hypothesis generator (its one real catch across two passes, `phenytoin -> lacosamide`, the other reviewers missed) and a poor verifier: treat it as a colleague whose every factual assertion is double-checked, never as a reference. More reasoning effort ("high"/"max") does not fix this — the failure is confabulated evidence, not shallow thinking.
- **Deploy**: GitHub Actions — PRs auto-deploy to a test environment; a push to `master` deploys to production (shinyapps.io) only after `R-CMD-check` has passed on it (`workflow_run` in `shiny-deploy-production.yaml`), and the deploy installs that exact commit (`@sha`), fails if the installed `RemoteSha` differs, and writes the SHA into the deployed `config.yml` as `commit`. The version and that commit are the first line of the debug log and the tooltip of the Source link (`stanpumpRBuild()`; the config first, the DESCRIPTION's `RemoteSha` as a fallback, since shinyapps.io does not carry it), so a live session can be matched to a commit. A manual run (`workflow_dispatch`) deploys the commit it is run on without the check.
- **Windows binary**: every push to `master` rebuilds a Windows binary zip (`.github/workflows/windows-binary.yaml`), installs it into an empty library, runs `.github/scripts/windows-smoke-test.R` under a timeout, and replaces the rolling release `windows-binary` (one publish at a time, skipped when master has moved past the build; asset `stanpumpR.zip`, one file for x64 and ARM since the package has no compiled code). It is the documented way to install on Windows (README, `inst/help/scripting.md`, `inst/apidocs/api.md`): a source install there can fail with a bare "lazy loading failed" because Windows 11 Smart App Control blocked a DLL it could not verify during the build.
- **Adding an R package**: add to `DESCRIPTION` first, then `renv::install("pkg")` + `renv::snapshot()`, commit `DESCRIPTION` + `renv.lock` together. For a package that isn't on CRAN, also add it under `Remotes:` in `DESCRIPTION` (e.g. `daattali/undomanager`) and install with `renv::install("user/repo")`, so the deploy can resolve it. A package used only by an optional entry point (plumber for the TCI API) goes in `Suggests`, is guarded with `requireNamespace()`, and is not snapshotted into `renv.lock`.


## The Help Tab (`R/help-*.R`, `inst/help/`)

The in-app help is a `bslib::nav_panel("Help")` with a sidebar (search + contents) and one `uiOutput`. Pages are either Markdown in `inst/help/<id>.md` (rendered by `shiny::markdown()`, i.e. commonmark — no pandoc, no MathJax) or generated from the code: one page per drug (`help-drugs.R` runs the drug model at six reference patients: volumes and clearances, half-lives and ke0, the extravascular routes' `ka`/bioavailability/lag, and for a Michaelis-Menten drug a **Saturable elimination** section giving Vmax, Km, the peripheral volume implied by `k23`/`k32` and the salt factors — without which the first two tables describe a saturable drug as a linear one, since its CL1 is only the limit below Km and its peripheral compartment is not V2), one per teaching scenario (`help-scenarios.R`), plus the drug index, scenario index and bibliography. `help-content.R` holds the registry (`helpStaticPages()`), the renderer and the search; `help-server.R` is called once from `app_server()`. Links between pages are `[text](help:page-id)`; `[text](scenario:id)` makes a button that calls `applyHelpScenario()`, which writes `doseTable()`/`eventTable()` and the inputs, then `bslib::nav_select()`s the Simulator. All clicks go through three delegated handlers in `inst/www/app.js` (`help_goto`, `help_scenario_load`, `investigator_show`), so the help adds no per-page inputs. `inst/help/README.md` is the authoring guide. Tests: `test-help-content.R`, `test-help-drugs.R`, `test-help-scenarios.R`.

**Investigators** (`R/help-investigators.R`): the bold names on `inst/help/investigators.md` are the registry (`helpInvestigatorRegistry()`: key = surname + first initial, so "Thomas Bouillon" and "Thomas W. Bouillon" are one person and the four Kims are four). `helpLinkInvestigators()` wraps each mention in `<a class="investigator-link" data-investigator="key">` on every help page (`helpPageUI()`), in the citation strings the drug models return (`citationItemHTML()`, so the References panel under the plot too) and in the bibliography; a bare surname links only when it is unique, and `HELP_INVESTIGATORS_CITATION_ONLY` (Shafer) is linked only with `context = "citation"`. The same pass links "GasMan" to its website (`HELP_TERM_LINKS`). The click shows `helpInvestigatorModal()`: every block of the page naming the person, by section, then their `references.md` entries. Adding an investigator is writing the name in bold on that page. Tests: `test-help-investigators.R`.
